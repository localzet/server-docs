# Tunnel: API и эксплуатация

Релиз [`v4.0.0`](https://github.com/localzet/Tunnel/releases/tag/v4.0.0) добавил общий предел 32 МиБ ожидающих данных на процесс брокера к лимиту 10 000 сообщений. Версия также запретила объекты и циклические массивы в PHP-serialized payload по умолчанию. В [`v4.0.1`](https://github.com/localzet/Tunnel/releases/tag/v4.0.1) debug-логи перестали содержать сообщения и сырые исключения. Текущий релиз — [`v4.0.2`](https://github.com/localzet/Tunnel/releases/tag/v4.0.2). Перед обновлением проверьте ограничения payload и совместимость компонентов на всех узлах.

Требуются PHP 8.1+ и Localzet Server `^7.0`. Сервер создаётся как `new localzet\Tunnel\Server($socketName, $debug = false, $allowObjectSerialization = false)`; при заданном socket name он регистрирует один worker через bootstrap Server. `Client` — статический API и рассчитан на один соединённый Tunnel endpoint в каждом PHP-процессе. Перед обновлением проверьте payload и приложение: по умолчанию Tunnel отвергает объекты и циклические массивы, если opt-in не включён на обеих доверенных сторонах.

## События

Сначала вызовите `Client::connect($socketName)`, затем регистрируйте callbacks через `on($event, $callback)`. `on()` одновременно оформляет подписку; для явного управления используйте `subscribe()` и `unsubscribe()`. `publish($events, $data, $is_loop = false)` отправляет событие подписчикам; `is_loop` выбирает round-robin режим публикации, а не гарантирует однократную обработку. `onConnect`, `onClose` и `onMessage` позволяют наблюдать lifecycle соединения.

## Очереди

`enqueue($channels, $data)` добавляет данные в именованную очередь. `watch($channels, $callback, $autoReserve = true)` начинает получать элементы; при авто-резервировании Tunnel запрашивает следующий элемент после завершения callback. `unwatch()` прекращает наблюдение, `reserve()` запрашивает элемент вручную. Очередь хранится только в RAM сервера, не является durable queue и теряется при рестарте. Для побочных эффектов используйте идемпотентные handlers; собственный механизм retry/dead-letter отсутствует.

Все очереди одного процесса делят общий предел в 10 000 ожидающих сообщений и 32 МиБ ожидающих данных. Размер учитывается по входному фрейму; при доставке нескольким каналам каждая поставленная копия учитывает этот размер. Если enqueue превысит любой предел, сервер не добавит ни одного сообщения из этого запроса; multi-channel запрос проверяется целиком. `Client::enqueue()` не возвращает подтверждение приёма, поэтому отправитель не может определить по результату вызова, была ли запись отклонена. Учитывайте это при проектировании повторной доставки и собственной обратной связи.

## Формат, безопасность и надёжность

Wire protocol по умолчанию сериализует данные PHP. Object deserialization закрыта и на сервере, и на клиенте. Не используйте `new Server(..., allowObjectSerialization: true)` и `Client::allowObjectSerialization()` с недоверенными peer. Передавайте скаляры и массивы; обе стороны должны договориться о формате. Протокол не имеет встроенной аутентификации или TLS, поэтому слушайте loopback либо изолированную сеть и ограничьте доступ внешними ACL.

Reconnect восстанавливает транспорт, но не обеспечивает durable delivery или exactly-once. Debug-логи содержат названия операций и статусы, но исключают тела запросов и сообщений. Тестируйте разрыв соединения, повторную подписку, конкурирующих consumers и shutdown в целевом приложении. Для Server 7 используйте `localzet/tunnel:^4.0`.
